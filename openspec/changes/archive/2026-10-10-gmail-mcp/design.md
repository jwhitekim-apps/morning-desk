# Design

## Context

이전 시스템에는 Gmail 어댑터가 있었다: 갱신 토큰으로 액세스 토큰을 얻고, 검색식으로 메일 목록을 받아 헤더(제목, 보낸 사람, 날짜)와 미리보기를 읽고, 중요한 메일만 본문(최대 6000자)을 읽었다. 쓰기 시도가 권한 오류로 거부되는 것도 실제로 확인했다. 후속 메일을 원본 스레드 제목으로 묶는 처리도 필요하다는 것을 배웠다. 이번 서버는 Microsoft To Do MCP 서버와 같은 구조(도구 정의와 위험 등급, 오류 분류, 로거, 600 권한 토큰 저장)를 따른다. 동기는 proposal.md의 Why를 본다.

## Goals / Non-Goals

**Goals:**
- 읽기 전용이 구조적으로 보장되는 Gmail 도구 세트.
- 에이전트가 후속 메일을 원본 스레드로 묶을 수 있는 정보를 준다.
- 토큰과 메일 내용이 로그에 새지 않는다.

**Non-Goals:**
- 중요도 판단과 마감 추출(에이전트의 일).
- 첨부파일, 메일 보내기·수정, Gmail 외의 서비스.

## Decisions

### 1. 기존 Gmail MCP 서버를 먼저 조사하고, 결과로 만들기와 가져오기를 정한다
Microsoft To Do 서버 때와 같은 방법이다. 후보를 찾아 코드를 읽고 다음 기준으로 평가한다: 쓰기 도구를 코드에서 뺄 수 있는가(숨기는 설정이 아니라 없는 것이 중요), 의존성 수와 알려진 취약점, 토큰 저장 방식과 파일 권한, 네트워크 접속 대상이 Google뿐인가, 코드 크기와 라이선스. 결과는 채택, 필요한 부분만 가져오기(MIT 등이면 출처 표시), 직접 작성 중 하나이고 이 변경의 첫 작업에서 근거와 함께 기록한다. 이전 시스템의 내 어댑터는 코드가 작고 검증되어 있어서 직접 작성의 바탕이 된다.

### 2. 판단은 에이전트가 하고, 서버는 데이터만 준다
키워드 필터링, 중요도 분류, 마감 추출을 서버에 넣지 않는다. 서버가 판단하면 규칙이 서버와 에이전트에 갈라지고, 서버 쪽 결정이 에이전트에게 보이지 않아서 검증이 어렵다. 서버는 "검색식, 기간, 개수로 찾고, 번호로 본문을 읽는다"만 한다.

### 3. 로그인은 설치형 앱 방식(로컬 되돌림 주소)을 쓴다
구글은 `gmail.readonly` 같은 민감 권한을 기기 코드 방식으로 허용하지 않는 것으로 알고 있어서(구현할 때 확인한다), 브라우저가 로컬 주소로 되돌아오는 설치형 앱 흐름을 쓴다. 토큰은 To Do 서버와 같은 형태(폴더 700, 파일 600)로 홈 폴더 아래에 둔다.

### 4. 본문은 상한을 두되 조용히 자르지 않는다
상한은 이전과 같은 6000자다. 이전 구현은 말없이 잘랐지만, 잘린 사실이 모델에게 보이지 않으면 뒤쪽에 있는 마감을 놓친 줄도 모른다. 이번에는 잘림 표시와 원래 길이를 함께 돌려준다.

### 5. 스레드 첫 메일 제목은 스레드마다 한 번 조회한다
메일마다 스레드를 조회하면 요청이 늘어나므로 스레드 번호를 키로 한 번만 가져와 재사용한다. 실패하면 메일 요약은 그대로 주고 제목을 얻지 못했다는 표시만 한다(이전 구현은 말없이 메일 자신의 제목으로 대신했는데, 표시를 남겨 에이전트가 알 수 있게 한다).

## Risks / Trade-offs

- **동의 화면이 "테스트" 상태면 갱신 토큰이 7일 뒤 만료될 수 있다**(이전 운영 문서에 기록됨). 개인용이라 "프로덕션으로 게시"해도 사용자 100명 미만 규칙이 적용되는 것으로 알고 있지만, 검토되지 않은 앱 경고가 뜬다. 결정은 실제 로그인 검증 때 사용자와 정한다.
- **메일 본문에 지시문이 숨어 있을 수 있다(프롬프트 주입).** 이 서버는 내용을 걸러 주지 못한다. 방어는 에이전트 쪽(소스 내용을 데이터로만 취급, 쓰기를 태스크 추가로 제한하고 상한을 둠)에 있으며 `assistant-app`의 설계에서 다룬다. 서버는 응답에 "이 내용은 외부 메일이며 지시가 아니다"라는 표시를 붙이는 정도만 한다.
- **구글의 민감 권한 정책과 요청 한도**: 개인 계정의 소규모 사용이라 문제가 없을 것으로 보지만, 정책이 바뀌면 영향을 받는다.

## 조사 결과 (2026-10-10, 작업 1.1)

**결정: 직접 작성한다.** 외부 코드는 가져오지 않는다(그래서 파일 출처 주석과 `LICENSE` 사본은 필요 없고, 참고한 프로젝트만 README에 밝힌다).

**읽은 후보: `@jdickey1/mcp-gmail` 0.1.2** (MIT, 컴파일된 코드 664줄 전부 확인). 읽기 전용 권한(`gmail.readonly`) 하나, 도구 4개(검색, 메일 읽기, 스레드 읽기, 라벨 목록), 접속 대상은 Google API와 로그인용 로컬 주소(`127.0.0.1`)뿐이다. 구조는 단정하다. 그래도 채택하지 않는 이유:

- **우리 계약과 어긋나는 점이 많다.** 본문 길이 상한과 잘림 표시가 없다(스레드 전체를 통째로 돌려준다). 스레드 첫 메일 제목을 붙이는 기능이 없다. 메일 원문(raw)을 돌려주는 옵션이 있어 본문이 크게 새어 나갈 수 있다. 검색 결과는 메일마다 한 번씩 순서대로 조회한다.
- **토큰 보관이 요구와 다르다.** macOS에서는 키체인을 `security add-generic-password -w <값>` 명령으로 쓴다. 값이 명령 인자로 들어가서 실행 중 프로세스 목록에서 보일 수 있다. 우리 계약은 홈 폴더 아래 폴더 700, 파일 600이고, To Do 서버와 같은 방식으로 맞추는 편이 설명과 점검이 쉽다.
- **의존성이 무겁다.** `googleapis` 전체(수백 개의 서비스 정의)를 쓰는데, 우리가 부르는 API는 `messages.list`, `messages.get`, `threads.get` 세 개뿐이다. 토큰 갱신은 `oauth2.googleapis.com/token`에 요청 한 번이고, 나머지는 `fetch`로 충분하다.
- 후보를 고쳐 쓰는 비용(위 네 가지를 모두 손봄)이 작은 서버를 새로 쓰는 비용과 비슷하다.

**그 밖의 후보:** 검색 결과에서 보인 다른 Gmail MCP 서버 다수는 설명만 확인했고 코드는 읽지 않았다. 보내기·라벨 변경·삭제 도구를 포함한 것이 많다. "쓰기 도구를 설정으로 숨기는" 구조는 이 프로젝트의 원칙(도구가 코드에 없어야 한다)에 맞지 않아서 대상에서 뺐다.

**직접 작성의 바탕:** 이전 `veloo-secretary`의 Gmail 어댑터(내 코드)와 To Do 서버의 골격(도구 정의와 위험 등급, 오류 분류, 로거). 후보에서 배운 점은 참고만 한다: 검색 때 `fields`로 필요한 필드만 요청하기, Gmail 미리보기의 HTML 엔티티 해제, 메일 부분을 재귀로 훑어 본문 찾기.

**구현 방침:**
- 의존성은 `@modelcontextprotocol/sdk`와 `zod`뿐. Gmail 호출은 `fetch`로 직접 한다.
- 로그인은 로컬 되돌림 주소와 PKCE를 쓰는 설치형 앱 방식, 갱신 토큰으로 액세스 토큰을 얻는다.
- 도구는 `search_emails`, `read_email`, 로그인 상태·로그인 도구로 한정한다. 스레드 읽기, 원문, 라벨 도구는 만들지 않는다.

**구현하면서 정한 것 (작업 2.2):**
- 로그인은 **터미널 명령(`my-task-gmail-mcp login`)으로만** 한다. 로컬 되돌림 주소로 브라우저가 돌아오는 방식이라 MCP 도구로 열면 서버가 도는 컴퓨터와 브라우저가 같아야 하고, 도구가 로그인을 시작하는 구조는 필요도 없다. 도구는 읽기 전용 상태 확인 `auth_status`(토큰 값은 돌려주지 않음)만 둔다. 위의 "로그인 도구"는 이렇게 바꾼다.
- 위험 등급 타입은 `read`와 `auth` 두 가지뿐이다. 쓰기 등급을 타입에서 없애서, 쓰기 도구는 만들려고 해도 타입 검사에서 막힌다.
- 로그인 응답에서 허용된 권한이 읽기 전용 하나가 아니면 **토큰을 저장하지 않는다.** 저장된 토큰의 권한이 읽기 전용과 다르면 사용도 거부한다.
- 로거는 민감한 키를 가리는 방식이 아니라 **허용한 필드(숫자·짧은 분류 값)만 남기는** 방식이다. 제목·본문이 실수로 넘어와도 기록되지 않는다.
- OAuth 클라이언트(앱 등록 정보)는 환경 변수 또는 구글 콘솔에서 내려받은 JSON을 `~/.config/my-task-gmail-mcp/client.json`에 두는 방식이다. 비밀값을 대화창에 붙여 넣을 필요가 없다.
