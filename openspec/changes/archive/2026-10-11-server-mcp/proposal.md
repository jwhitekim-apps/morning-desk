# Proposal

## Why

비서(`assistant-app`)는 집 서버에서 하루 한 번 돌고, 학교 서버의 로컬 모델을 호출한다. 서비스가 죽어 있거나, 모델 서버의 포트·키·모델 설정이 어긋나 있거나, 컨테이너가 조용히 오류를 내고 있어도 지금은 아무도 모른다. 이전 시스템에서도 "실패를 숨기지 않는다"는 원칙이 중요했고, 모델이 쓸 때만 메모리에 올라가는 구조라 점검을 잘못 설계하면 점검이 모델을 올려 버린다. 비서가 아침 브리핑에 "서버 상태" 한 줄을 넣고, 이상이 있을 때만 눈에 띄게 알릴 수 있도록 **서버 상태를 읽기 전용으로 점검하는 MCP 서버**를 만든다.

## What Changes

- `mcp/server/`에 **서버 점검 전용 MCP 서버**를 만든다. 집 서버에서 비서와 같은 컴퓨터에서 돌고, 원격 명령 실행(SSH)은 쓰지 않는다. 점검 기능은 사용자가 정한 세 가지다.
  1. **서비스 active 확인**: 설정에 적은 주소(HTTP)와 포트(TCP)의 응답 여부와 응답 시간, 설정에 적은 도커 컨테이너의 실행 상태(실행 중, 재시작 횟수, 건강 검사 결과).
  2. **LLM 점검**(학교 서버): 포트가 열려 있는지, API가 응답하는지, 키가 유효한지, 기대하는 모델이 목록에 있는지. **모델을 호출하지 않는다**(점검이 모델을 메모리에 올리지 않게).
  3. **도커 로그 확인**: 설정에 적은 컨테이너의 최근 시간(기본 24시간) 로그에서 오류 줄 수와 짧은 요약. 원문은 돌려주지 않는다.
- 점검 대상(주소, 포트, 컨테이너 이름, 모델 이름)은 **설정 파일에 적은 목록만** 허용한다. 모델이 임의의 대상을 지정할 수 없다.
- 도구 표면은 읽기로 고정하고 허용 목록 테스트가 지킨다. 명령 실행, 재시작, 로그 삭제 같은 도구는 만들지 않는다.
- 이름은 `server-mcp`로 정했다(사용자 결정). 모든 MCP가 "MCP 서버"라서 혼동될 수 있으므로, 도구 이름에 하는 일을 넣고(`check_services`, `check_llm`, `summarize_docker_logs`) 응답에는 항상 점검 대상의 이름을 적는다.
- **범위 밖**: 학교 서버 안쪽(GPU, 서버 로그, 설정 파일)은 SSH가 필요하고 효용이 낮다고 판단해 제외한다. 모델 호출을 통한 점검, 서비스 재시작이나 복구 같은 쓰기, 알림 전송(비서가 한다), 맥북 같은 다른 컴퓨터의 로컬 파일, systemd 서비스 점검(필요해지면 별도 변경).

## Impact

- 새 코드: `mcp/server/` (TypeScript, Node 20 이상, 표준입출력 MCP 서버).
- 외부 시스템: 점검 대상 서비스의 HTTP 주소와 TCP 포트, 학교 서버의 OpenAI 호환 API(`/v1/models`), 집 서버의 도커(`docker ps`/`inspect`/`logs` 읽기).
- 비밀: 학교 LLM의 API 키(환경 변수). 키는 응답과 로그에 나타나지 않는다.
- 위험: 도커를 쓰는 계정은 사실상 관리자 권한이다. 서버가 고정된 읽기 명령만 쓰도록 구조로 막지만, 권한을 더 줄이는 방법(읽기 전용 도커 소켓 프록시)을 설계에서 검토한다. 로그에는 외부 입력(메일 내용 등)이나 비밀이 섞일 수 있어서 요약과 마스킹을 거친다.
- 연결: `assistant-app`이 이 서버를 사전 점검과 브리핑의 "서버 상태" 구역에 쓰도록 연결하는 일은 `assistant-app`의 변경에서 다룬다.
- 전제: 학교 서버의 모델은 쓸 때만 메모리에 올라간다(사용자 확인). 그래서 LLM 점검은 모델 목록 조회까지만 한다.
