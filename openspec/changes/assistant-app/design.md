# Design

## Context

이전 시스템은 Vercel 함수 + Gemini로 돌았다. 메일을 키워드로 거르고 모델로 판단해 벨루에 태스크를 추가하고, 규칙으로 순위를 매겨 카톡 보고를 만들었다. 여기서 확정된 좋은 결정들이 있다: 위임 정책(읽기는 자유, 태스크 추가는 알리고 수행, 수정·삭제는 도구로 주지 않음), 실패를 숨기지 않기, 구역 단위로 나눈 말풍선, 마감이 불명확한 일도 마감 없는 태스크로 만들기, 같은 스레드의 일 합치기, 처리한 소스 기록, 드라이런. 이번에는 입력 창구가 To Do로 옮겨 가고, 모델이 학교 서버의 Qwen으로 바뀌며, 데이터 소스가 MCP 서버로 분리된다. 동기는 proposal.md의 Why를 본다.

## Goals / Non-Goals

**Goals:**
- 하루 한 번, 사람 없이도 소스를 훑어 브리핑을 보낸다.
- 모델의 실수가 중복, 소음, 잘못된 날짜로 번지지 않는 구조.
- 모델이나 소스가 실패해도 브리핑은 나가고 실패는 보인다.

**Non-Goals:**
- 입력 화면, 대화형 답장, 음성, 태스크 수정·삭제·완료.
- 임베딩 기억과 모델 주도의 자유로운 도구 사용(스파이크 결과를 보고 후속에서 판단).

## Decisions

### 1. 집 서버에서 하루 한 번 실행한다
Vercel은 함수 시간 제한(무료 5분)이 있고 MCP 서버를 자식 프로세스로 띄우기도 어렵다. 집 서버(벨루를 돌리는 컴퓨터)는 항상 켜져 있고 시간 제한이 없으며 인터넷으로 나가는 연결만 필요하다. 시스템 타이머나 크론으로 하루 한 번 실행하고, 같은 프로그램을 수동으로도 실행한다. 실행할 때 MCP 서버들을 표준입출력 자식 프로세스로 띄운다.

### 2. 수집은 코드가, 판단은 모델이 한다
사용자의 구상은 "로컬 LLM이 MCP를 쥐고 있는" 것이다. 그러나 로컬 모델의 도구 호출 정확도가 아직 측정되지 않았고, 모델이 어떤 도구를 몇 번 부를지 정하면 실행마다 달라져서 검증과 재현이 어렵다. 그래서 시작은 이렇게 나눈다. 코드가 **정해진 순서로** 각 소스의 도구를 호출해 데이터를 모으고(결정적), 모델은 모인 데이터를 읽고 **정해진 JSON 구조로** 후보와 한마디를 낸다. 모델 출력은 스키마로 검증한다. 스파이크(첫 작업)에서 모델 주도의 도구 호출이 믿을 만한 수준인지 재고, 충분하면 후속 변경으로 확장한다. 이 결정은 구상과 다르므로 검토 때 사용자의 판단을 구한다.

### 3. 쓰기는 모델이 아니라 코드가 최종 결정한다
모델은 태스크 후보(이름, 마감, 출처, 근거 문장)만 낸다. 코드가 중복 확인(이름·마감 같음), 스레드 합치기, 출처 문구 부착, 실행당 상한 적용을 하고 나서 To Do의 추가 도구를 호출한다. 모델 출력이 곧바로 도구 호출이 되지 않는다.

### 4. 소스 내용은 지시가 아니라 데이터로 취급한다
메일, 이슈, 논문 제목에 "이전 지시를 무시하고…" 같은 문장이 숨어 있을 수 있다(프롬프트 주입). 방어는 겹겹이 한다. 소스 내용은 구분 표시 안에 넣고 모델에게 그 안의 지시는 따르지 말라고 알린다. 모델이 할 수 있는 행동 자체가 후보 제안뿐이라 최악의 경우에도 태스크 몇 개가 잘못 후보가 되는 정도다. 코드의 상한과 중복 확인, 제목 길이 제한이 한 번 더 막는다. 다음 실행에서 사람이 볼 수 있도록 추가한 태스크는 브리핑에 모두 나열한다.

### 5. 모델 연결과 모델 선택
OpenAI 호환 `/v1/chat/completions`로 호출한다. 기본은 빠른 모델(`qwen3.6:35b-a3b`), 어려운 판단만 큰 모델(`qwen3.8:27b`)을 쓰는 안을 스파이크로 비교해 정한다. 호출마다 제한 시간을 두고, 응답이 스키마에 맞지 않으면 한 번만 다시 요청한다. 본운영은 HTTPS 주소(`llm.2joon.com`)만 쓰고 평문 주소와 임시 포트(3389)는 시험에만 쓴다.

### 6. 모델이 없어도 브리핑이 나간다
모델 호출이 실패하거나 시간 초과가 나면 To Do에서 읽은 오늘·임박·밀린 목록만으로 결정적 브리핑을 만들어 보내고, 모델 없이 만들었다는 표시와 실패 원인을 실패 구역에 올린다. 이전 시스템의 규칙 기반 순위를 일부 다시 쓸 수 있다.

### 7. 어제 기억은 로컬 파일에 둔다
날짜별 요약(보고한 먼저 할 일, 추가한 태스크, 던진 질문)을 파일 권한 600의 로컬 JSON으로 저장한다. 임베딩 기억 검색은 후속이다. 사용자가 파일을 지우면 기억이 초기화된다.

### 8. 말풍선 만들기는 순수 함수다
구역 단위로 말풍선에 담는 규칙(구역 이름 한 줄, 항목은 한 줄씩, 구역을 쪼개지 않음, 통수 초과 시 뒤쪽 구역 제외, 순서 표시)은 이전 시스템에서 확정되었다. 내 코드라서 다시 써서 가져오고, 입력과 출력만 있는 순수 함수로 테스트한다.

### 9. 병행 운영으로 비교하고 퇴역한다
이전 Vercel 시스템은 아직 매일 아침 돌고 있다. 병행 기간에는 새 시스템을 드라이런 또는 별도 시간대로 돌려 결과를 나란히 보고, 7일 동안 다음을 사용자가 평가한다: 놓친 일정, 잘못 추가한 태스크, 중복, 읽기 쉬움, 실패가 보이는지. 만족하면 Vercel 크론을 끄고 프로젝트를 정리한다. 두 시스템이 같은 메일에서 서로 다른 곳(벨루, To Do)에 태스크를 만들어 이중으로 쌓이지 않게, 병행 기간에는 새 시스템의 태스크 추가를 끄고 비교만 하는 단계를 먼저 둔다.

## Risks / Trade-offs

- **로컬 모델의 품질이 기대에 못 미칠 수 있다.** 스파이크에서 구조화 출력 준수율, 날짜 정확도, 소요 시간을 먼저 재고 기준에 못 미치면 구조를 다시 정한다.
- **학교 서버에 의존한다.** 꺼지거나 방화벽이 바뀌면 모델이 없다. 결정 6이 브리핑을 지켜 주지만 한마디와 감지는 빠진다. 사용 규정도 사용자가 확인한다.
- **카톡 알림이 울리지 않는 문제가 남는다.** 브리핑이 나가도 안 읽힐 수 있다. 별도 변경으로 대안 경로를 정한다.
- **소스가 늘수록 모델에 넣을 글이 길어진다.** 로컬 모델의 문맥 길이는 한정되어 있어서, 소스별로 따로 요약한 뒤 합치는 단계를 둔다.
- **"모델이 MCP를 쥔다"는 구상과 다르게 시작한다.** 신뢰도를 재고 나서 점진적으로 모델의 재량을 늘린다.
