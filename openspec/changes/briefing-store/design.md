# Design

## Context

- 비서(`app/`)는 하루 한 번(기본 낮 12시) 소스를 읽고 모델이 후보를 제안하면 코드가 규칙으로 정해 카톡 나에게 보내기로 브리핑을 보낸다. 기록으로 남는 것은 어제 기록 파일(`memory.json`: 어제 한 일, 처리한 소스, 마지막 전송일)뿐이고, 브리핑 본문은 어디에도 저장되지 않는다.
- Archi Studio(새 웹앱)의 `briefing` 명세는 "앱은 브리핑을 읽기만 하고 비서가 DB에 기록한다"로 정해져 있다. 테이블은 `archi_briefings`(하루 한 건: 날짜, 요약, 본문)와 `archi_briefing_papers`(언급한 논문)이고, 같은 날짜는 한 건만 허용한다(`unique(user_id, date)`). 정의는 Archi Studio의 `docs/api/data-model.md` 3.10절에 있다.
- 이 저장소의 위임 정책은 쓰기를 "To Do 태스크 추가"와 "카톡 나에게 보내기"로만 허용한다. 함수가 코드에 없어야 하고(플래그로 숨기는 방식 금지), 모듈마다 허용 목록 시험이 있고, 앱이 받는 함수는 `app/test/run.test.ts`가 고정한다. 폴리오 모듈의 시험은 `.rpc(`와 POST를 아예 금지한다.
- 이미 비서는 같은 Supabase 프로젝트의 `folio_papers`를 폴리오 모듈로 **읽고** 있다(`FOLIO_SUPABASE_URL`, `FOLIO_SUPABASE_KEY`).
- 이 저장소의 `AGENTS.md`는 "다른 프로젝트의 일은 그 프로젝트에서 계획한다"고 정한다. 그래서 이 change는 비서 쪽 코드, 명세, 문서만 다루고, DB 함수와 역할은 Archi Studio의 `archi-studio-briefing`이 만든다. 둘 사이의 약속(호출 계약)은 결정 3에 적는다.

## Goals / Non-Goals

**Goals**
- 비서가 하루 브리핑을 Archi Studio DB에 기록한다. 쓰기는 **DB 함수 하나를 부르는 요청 하나**로 고정한다.
- 새 쓰기 권한이 코드와 시험에서 좁게 고정되어, 수정, 삭제, 다른 테이블 쓰기, 다른 사용자 데이터 쓰기가 불가능함이 시험으로 증명된다.
- 저장이 실패해도 카톡 브리핑은 나간다. 실패는 숨기지 않는다.
- 카톡에는 요약과 링크만 더한다.

**Non-Goals**
- Archi Studio 쪽 DB 함수, 역할, 읽기 정책, 화면(그 저장소의 change가 맡는다).
- 지난 브리핑의 소급 저장, 저장된 브리핑의 수정과 삭제, 서버 크론 변경.
- 모델이 저장을 직접 호출하는 것. 모델 출력은 지금처럼 쓰기로 직접 이어지지 않는다(코드가 정한다).

## Decisions

### 1. 쓰기는 테이블 직접 쓰기가 아니라 DB 함수 호출 하나로 한다
| 방식 | 장점 | 단점 |
|---|---|---|
| 테이블에 직접 insert/upsert(PostgREST) | 모듈이 단순하다 | 테이블 두 개에 대한 쓰기 권한이 필요하고, 논문 번호 변환과 검증이 비서 코드에 들어간다 |
| **DB 함수 `archi_save_briefing` 호출(rpc)** | 요청이 한 종류라 코드와 시험에서 고정하기 쉽다. 검증, 같은 날 덮어쓰기, 논문 번호 변환을 DB 안에서 한 번에 한다. 접속 키 권한을 "이 함수 실행"으로만 좁힐 수 있다 | Archi Studio 쪽에 함수를 먼저 만들어야 한다 |

추천은 **함수 호출**이다. 폴리오 모듈의 시험이 `.rpc(`를 금지하는 것은 폴리오 모듈이 읽기 전용이기 때문이므로 그대로 두고, 쓰기 모듈을 따로 만든다(결정 2).

### 2. 새 모듈 `sources/briefing-store`로 분리한다
폴리오 모듈에 쓰기를 넣지 않는다. 읽기 전용 모듈의 시험(`.rpc(`와 POST 금지)을 약하게 만들지 않고, 새 쓰기 권한이 한 곳에 모여 허용 목록 시험이 한 파일로 끝난다. 모듈은 `saveBriefing` 하나만 내보내고(`BRIEFING_STORE_ALLOWED = ["saveBriefing"]`), HTTP 호출은 한 파일의 한 곳, 메서드는 POST 하나, 경로는 `/rest/v1/rpc/archi_save_briefing` 하나로 시험이 고정한다. 의존성은 다른 모듈처럼 인자로 받는다(`fetchFn`, `sleep`, `logger`).

### 3. 함수 호출 계약(Archi Studio 쪽이 만들 것)
비서가 부르는 모양이다. Archi Studio의 `archi-studio-briefing`이 이 약속대로 만든다.

```
POST {BRIEFING_STORE_SUPABASE_URL}/rest/v1/rpc/archi_save_briefing
본문(JSON): { "p_user_id": uuid, "p_date": "YYYY-MM-DD", "p_summary": text,
              "p_body": text, "p_item_keys": [text, ...] }
응답(JSON): { "id": uuid, "linked": 연결된 논문 수, "skipped": 매칭되지 않은 항목 번호 수 }
```

- 같은 `(p_user_id, p_date)`면 그 한 건의 요약, 본문, 논문 목록을 바꾼다(없으면 만든다). 다른 날짜와 사용자는 건드리지 않는다.
- `p_item_keys`는 그 사용자의 `papers`에서 `item_key`로 찾아 `archi_briefing_papers`에 연결하고, 못 찾은 것은 무시하고 개수만 `skipped`로 돌려준다.
- `security definer`(함수 만든 사람의 권한으로 실행)이고 검색 경로를 고정한다. 실행 권한은 전용 역할(결정 4)에만 준다.
- 이 약속과 다르게 만들어지면 `function_missing`이나 `validation_error`로 드러나고, 시험(가짜 서버)은 이 모양을 기준으로 한다.

### 4. 접속 키의 범위: 선택지와 추천
| 선택지 | 키가 뚫리면 | 준비 |
|---|---|---|
| A. 서비스 키(관리자 권한) | DB 전체가 읽히고 써진다(벨루 운영 데이터 포함) | 이미 있음. 폴리오 모듈의 현재 방식 |
| **B. 전용 DB 역할 + 그 역할로 서명한 장기 키** | 이 함수 하나만 부를 수 있고, 다른 테이블에는 어떤 권한도 없다. 키를 폐기하려면 역할의 실행 권한을 회수한다 | Archi Studio 쪽에서 역할과 권한을 만들고 한 번 키를 발급한다 |
| C. Archi Studio 사용자(주인)로 로그인한 세션으로 호출 | 한 사용자 권한으로 제한 | 비서가 로그인과 토큰 갱신 흐름을 가져야 해서 복잡하다 |

추천은 **B**다. 폴리오 모듈 README의 방침(개발·시험 중에는 서비스 키 허용, 운영 전에 제한된 키로 교체)을 같게 따른다. 이 계획을 쓰는 동안 B가 Supabase 호스팅에서 실제로 되는지(사용자 지정 역할로 서명한 키를 받아 주는지)는 **확인하지 못했다**. 안 되면 A로 시작하되 이 모듈만 키를 읽고, 운영 서버에서 `.env.local`(권한 600)에만 두고, 로그와 오류에 키가 나오지 않음을 시험으로 고정한다. 이 판단은 구현 첫 작업에서 로컬 Supabase로 확인한다.

### 5. 저장하는 범위는 카톡으로 나가는 범위와 같다
저장은 새로운 정보 유출 경로이므로 범위를 좁힌다. 본문은 카톡 말풍선과 같은 내용(제목 수준)만 저장하고, 메일 본문, 보낸 사람, 알림 내용은 저장하지 않는다. Supabase 클라우드는 LLM이 아니므로 "소스 내용은 로컬 LLM에만"이라는 기존 원칙과 충돌하지 않지만, 개인정보를 외부 서비스에 두는 일이라는 점은 같다(카톡 `improve-briefing` 결정 5와 같은 판단). 이미 같은 DB에 폴리오 논문 목록이 있다. 다만 이 DB는 벨루 운영 프로젝트와 같은 프로젝트라서, 앱 쪽 읽기 정책이 "내 브리핑만 읽는다"를 지켜야 한다(Archi Studio 쪽 몫이고, 이 change는 그 사실을 문서에 적는다).

### 6. 명세는 새 capability로 두고, 겹치는 문구는 구현 때 맞춘다
`briefing-store-tools`를 새 capability로 둔다. "쓰기는 태스크 추가와 나에게 보내기뿐"이라는 문구는 `AGENTS.md`(메인 문서)와 보관되지 않은 `assistant-app`의 문서에 있을 수 있어서 MODIFIED로 고칠 메인 명세가 없다(확인하지 못함: 구현 첫 작업에서 `grep`으로 모든 위치를 찾는다). `AGENTS.md`의 위임 정책과 파일 구조 문구는 구현에서 고치고, `assistant-app`의 해당 문구는 그 change의 문서를 먼저 고쳐서(AGENTS.md의 "미보관 change의 작은 수정" 규칙) 이 change를 가리키게 한다.

### 7. 요약은 코드가 결정적으로 만든다(모델 사용 없음)
목록에 보일 한 줄 요약(1~200자)은 숫자만으로 코드가 만든다. 예: "10월 18일 브리핑: 오늘 할 일 3건, 새로 찾은 일 2건, 점검 이상 1건". 내용(제목)은 요약에 넣지 않는다. 모델이 쓰게 하면 실패와 지연이 저장에 번지고, 모델 출력이 저장 내용에 직접 이어지는 길이 생기기 때문이다(위임 정책: 모델 출력은 쓰기로 직접 이어지지 않는다).

### 8. 하루 실행의 순서와 실패 처리
본문 만들기 → **저장**(켜져 있고 드라이런이 아닐 때) → 성공하면 링크를 말풍선 끝에 덧붙임 → 카톡 전송 → 기억 파일 저장. 링크가 저장 결과(브리핑 번호)에 의존하므로 저장이 카톡보다 앞선다. 저장이 실패하면 링크 없이 그대로 보내고, 실패 구역에 오류 코드로 한 줄을 남긴다. 저장은 같은 날 한 번만 일어난다(`already-sent`이면 건너뛰고, `force` 재실행은 덮어쓴다). 호출 시간 제한은 다른 모듈처럼 앱의 `withTimeouts`가 건다.

### 9. 재시도는 안전한 범위에서만
같은 날짜를 덮어쓰는 호출이라 같은 요청을 다시 보내도 결과가 같다(멱등). 그래서 서버 일시 장애(5xx), 요청 한도 초과(429), 연결 오류에서만 최대 2번 다시 시도한다(총 3번, 대기는 짧게 늘린다). 인증 오류, 함수 없음, 입력 오류는 다시 시도하지 않는다.

### 10. 설정
| 이름 | 설명 |
|---|---|
| `ASSISTANT_SAVE_BRIEFING` | `1`이면 저장한다. 기본 꺼짐(`ASSISTANT_CREATE_TASKS`와 같은 방식의 병행 운영 단계) |
| `BRIEFING_STORE_SUPABASE_URL` | Archi Studio가 쓰는 Supabase 프로젝트 주소. https만 허용(localhost 제외) |
| `BRIEFING_STORE_KEY` | 접속 키(결정 4) |
| `BRIEFING_STORE_USER_ID` | 브리핑 주인, 즉 Archi Studio 사용자 번호(uuid) |
| `ARCHI_STUDIO_BASE_URL` | 링크용 앱 주소. 비우면 링크 없이 저장만 한다 |

이 값들은 자동으로 갱신되는 토큰이 아니라 사람이 정하는 설정이므로 `.env.local`의 토큰 구역(`shared/src/env-file.ts`가 고쳐 쓰는 줄)이 아니라 설정 구역에 둔다. 모듈은 자기 설정만 앱에서 받는다.

## Risks / Trade-offs

- [키가 서비스 키이면 뚫렸을 때 벨루 운영 데이터까지 닿는다] → 결정 4의 전용 역할을 추천하고, 서비스 키는 개발·시험까지만 허용한다. 홈 서버를 켜기 전에 교체하는 것을 구현 작업의 완료 조건으로 둔다.
- [Archi Studio 쪽 함수가 아직 없으면 켰을 때 매일 실패한다] → 기본 꺼짐이고 `function_missing`으로 구분되며 카톡은 나간다. 켜기 전에 로컬 Supabase에서 함수를 먼저 시험한다.
- [브리핑 내용이 클라우드 DB에 쌓인다] → 카톡과 같은 범위(제목까지)로 제한하고(결정 5), 로그에는 건수와 소요 시간만 남긴다.
- [`BRIEFING_STORE_USER_ID`를 잘못 설정하면 엉뚱한 사용자 브리핑이 된다] → 외래 키 위반이면 `user_unknown`으로 실패하고 아무것도 저장되지 않는다. 존재하는 다른 사용자 번호를 넣은 경우는 막을 수 없으므로 설정 확인을 구현 완료 조건에 둔다.
- [같은 날 덮어쓰기로 이전 내용이 사라진다] → 의도된 동작이다(브리핑은 하루 한 건). 이력 보존이 필요해지면 그때 따로 정한다.
- [안전 정책을 약하게 만드는 선례가 될 수 있다] → 새 쓰기를 DB 함수 하나로, 시험으로 고정하고, 삭제·수정·다른 테이블 쓰기가 계속 없다는 시험을 더한다. 쓰기 함수를 더 늘리려면 이 목록과 명세를 다시 의도적으로 고쳐야 한다.

## Migration Plan

1. Archi Studio의 `archi-studio-briefing`이 `archi_save_briefing` 함수와 전용 역할을 로컬 Supabase에서 먼저 만들고 시험한다(이 change의 계약, 결정 3).
2. 이 change를 구현한다. 시험은 가짜 서버(`fetchFn`)로 하고 네트워크는 쓰지 않는다. 구현이 끝나면 `npm run typecheck && npm run lint && npm test && npm run build`가 통과한다.
3. 로컬 Supabase에 대해 한 번 실제로 저장해 보는 확인은 주인과 함께 하는 별도 작업으로 한다(`AGENTS.md`: 실제 서비스 확인은 시험이 아니라 따로 한다).
4. 운영 DB에 Archi Studio 마이그레이션이 적용된 뒤(Archi Studio의 배포·이전 change) 집 서버 `.env.local`에 설정을 넣고 먼저 드라이런으로 확인하고, 그다음 `ASSISTANT_SAVE_BRIEFING=1`로 켠다.
5. 되돌리기: `ASSISTANT_SAVE_BRIEFING`을 지우거나 0으로 바꾸면 저장이 멈추고 카톡 브리핑은 그대로다. 이미 저장된 브리핑은 남는다.

## Open Questions

1. **접속 키 방식**: 추천은 전용 DB 역할과 그 역할의 장기 키(B)다. Supabase 호스팅에서 되는지는 구현 첫 작업에서 로컬 Supabase로 확인하고, 안 되면 서비스 키로 시작한다.
2. **링크 경로**: 이 명세는 `<앱 주소>/log/<브리핑 번호>`로 가정했다. 화면 change(`archi-studio-ui-briefing`)의 실제 경로와 맞춰야 한다. 추천은 그 경로를 따르는 것이고, 경로를 설정으로 빼지는 않는다.
3. **같은 날 다시 저장할 때 이전 내용 보존**: 추천은 덮어쓰기(하루 한 건)다.
4. **저장 범위에 대한 주인의 확인**: 카톡과 같은 범위(제목까지)를 클라우드 DB에 저장해도 되는지 주인이 확인해야 한다. 추천은 같은 범위로 제한하는 것이다.
5. **매칭되지 않은 논문 번호**: 추천은 무시하고 개수만 로그에 남기는 것이다(오류로 하면 폴리오 동기화가 늦은 날 브리핑 저장이 실패한다).
6. **기존 `assistant-app` 문서의 쓰기 문구 위치**: 구현 첫 작업의 `grep`으로 찾는다. 있으면 그 change 문서를 먼저 고친다.
