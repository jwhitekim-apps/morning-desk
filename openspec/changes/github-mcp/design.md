# Design

## Context

GitHub에는 내게 해당하는 일을 모아 주는 조회가 이미 있다: 내게 리뷰가 요청된 PR 검색, 내게 배정된 이슈와 PR 검색, 알림 목록, 그리고 마일스톤의 마감일(`due_on`). 이 컴퓨터에는 `gh`가 `jwhitekim`으로 로그인되어 있다. 공식 GitHub MCP 서버와 여러 커뮤니티 서버가 있고, 공식 서버는 도구 묶음(툴셋)과 읽기 전용 모드를 설정으로 제한할 수 있는 것으로 알고 있다(조사 때 확인한다). 동기는 proposal.md의 Why를 본다.

## Goals / Non-Goals

**Goals:**
- 쓰기 도구가 노출될 수 없다는 것을 검증할 수 있는 읽기 전용 GitHub 도구.
- 일정 감지에 필요한 항목(리뷰 요청, 배정, 마일스톤 마감, 알림)만.

**Non-Goals:**
- 쓰기 전반, 코드 읽기, 저장소 관리.

## Decisions

### 1. 세 가지 방식을 조사하고 비교해서 고른다
(A) 공식 서버를 읽기 전용 설정으로 쓴다: 코드를 만들 필요가 없고 유지가 쉽다. 단 설정이 쓰기 도구를 실제로 숨기는지, 필요한 조회가 있는지, 의존성이 무엇인지 확인해야 한다. (B) `gh api`를 감싼 얇은 서버: 고정된 조회 명령만 실행한다. 사용자 입력이 명령에 섞이지 않게 쉘 없이 인자를 배열로 넘기고(`execFile`) 허용된 경로만 호출한다. (C) REST를 직접 호출하는 작은 서버: 의존성이 가장 적고 호출을 완전히 통제한다. 선택의 1순위 기준은 **쓰기 도구가 존재하지 않음을 테스트로 보장할 수 있는가**이다. A가 이 기준을 충족하면 A를 쓰고 이 변경은 설정과 검증 테스트가 되고, 충족하지 못하면 C를 우선한다(B는 외부 프로세스 호출이라 위험이 한 단계 더 있다).

### 2. 인증은 읽기 전용 토큰을 따로 쓴다
`gh`의 기존 로그인 토큰은 보통 쓰기 권한까지 가진다. 에이전트용으로는 필요한 저장소에 대한 읽기 권한만 가진 fine-grained 토큰을 따로 만들어 쓰는 것을 원칙으로 한다. 토큰을 만드는 일은 GitHub 설정에서 사용자가 직접 한다.

### 3. 알림 조회는 읽음 표시를 바꾸지 않는다
조회가 상태를 바꾸면 사용자가 보던 알림이 사라진다. 읽기만 하는 호출만 쓰고 읽음 표시 호출은 도구로 노출하지 않는다.

### 4. 결과는 개수 상한을 둔다
항목이 많으면 상한까지만 주고 잘림 표시를 한다. 에이전트에게는 가까운 마감과 최근 갱신이 중요하므로 정렬 기준을 갱신 최신순으로 한다.

## Risks / Trade-offs

- **공식 서버의 기본 구성에는 쓰기 도구가 포함된다.** 읽기 전용 설정을 켜도 일부가 남는지 직접 도구 목록으로 검증하기 전에는 쓰지 않는다.
- **토큰 권한이 넓으면 모델의 실수 한 번이 저장소 변경으로 이어질 수 있다.** 결정 2로 줄이고, 서버가 읽기 전용 도구만 갖도록 이중으로 막는다.
- **비공개 저장소의 제목과 본문이 로컬 모델에 들어간다.** 외부 LLM으로는 보내지 않는다는 전제를 에이전트 변경이 지킨다. 어느 저장소를 포함할지는 설정으로 제한한다.
- **이슈 본문과 PR 설명에도 지시문이 숨어 있을 수 있다(프롬프트 주입).** 방어는 에이전트 쪽에 있다.

## 조사 결과 (2026-10-10, 작업 1.1)

**시험 대상:** 공식 `github/github-mcp-server` v2.0.2(MIT, 2026-10-08 릴리스). 공식 릴리스 바이너리(`github-mcp-server_Darwin_arm64.tar.gz`, 8.8MB)를 임시 폴더에 받아 체크섬(SHA-256)이 공식 값과 일치하는 것을 확인했다. **실제 토큰은 쓰지 않았다**: 환경을 비우고 더미 토큰과 빈 홈 폴더로만 실행해서 `tools/list`만 호출했고, 시험이 끝난 뒤 바이너리를 삭제했다(설치하지 않음). 도구 호출 결과(응답의 필드 구성)는 실제 토큰이 필요해서 시험하지 못했다.

| 구성 | 노출된 도구 | 쓰기 도구 |
|---|---|---|
| 기본 | 46개 | **19개** (`create_pull_request`, `merge_pull_request`, `push_files`, `delete_file`, `add_issue_comment`, `issue_write`, `pull_request_review_write` 등) |
| `--read-only` | 27개 | 0개 |
| `--read-only --toolsets context,issues,pull_requests,notifications,users` | 16개 | 0개 |

세 번째 구성의 16개: `get_label`, `get_me`, `get_notification_details`, `get_team_members`, `get_teams`, `issue_read`, `list_issue_fields`, `list_issue_types`, `list_issues`, `list_notifications`, `list_pull_requests`, `pull_request_read`, `search_issues`, `search_pull_requests`, `search_users`, `ui_get`. 모두 `readOnlyHint=true`이고 쓰기로 보이는 이름은 없다.

**판정:**
- 기준 1(쓰기 도구가 존재하지 않음을 보장할 수 있는가): **충족한다.** 기본 구성에는 쓰기 도구 19개가 있고(위험이 실재함), `--read-only`가 이를 실제로 모두 숨긴다.
- 필요한 조회가 있는가: 리뷰 요청(`search_pull_requests`의 `review-requested:@me`), 배정(`search_issues`의 `assignee:@me`), 알림(`list_notifications`, 읽기 전용)은 있다. 마일스톤 마감일과 "리뷰를 요청한 사람"이 응답에 들어 있는지는 실제 토큰 없이는 확인하지 못했다.
- 한계: 16개 도구는 모두 일반 검색·읽기라서 "나에게 해당하는 일"만으로 좁혀지지 않는다(아무 저장소의 이슈나 PR을 검색할 수 있다). 응답이 큰 JSON이라 로컬 모델의 문맥을 많이 차지할 수 있다. 개수 상한과 "잘렸다"는 표시, 요청 한도 초과의 다시 시도 시각 같은 이 변경의 명세 항목을 설정으로 맞출 수 없다.

## 결정과 새로 알게 된 것 (2026-10-10, 작업 1.2)

**결정: 직접 작성한다.** 사용자가 정했다. 공식 서버는 읽기 전용 구성에서 쓰기 도구가 없다는 기준 1은 충족했지만, 위 한계(일반 검색 도구 16개, 큰 응답, 명세의 상한·잘림 표시·다시 시도 시각을 설정으로 맞출 수 없음)가 있어서 REST를 직접 부르는 작은 서버로 간다. 의존성은 MCP SDK와 zod뿐이고 GET만 쓴다. 공식 서버의 코드는 가져오지 않는다(그래서 출처 표시 의무는 없고, 참고한 사실만 README에 밝힌다).

**알림은 fine-grained 토큰으로 조회할 수 없다.** 공식 문서(알림 API)에 "이 엔드포인트는 personal access token (classic)만 지원한다"고 적혀 있고, 필요한 권한은 `notifications` 또는 `repo`다. 따라서 토큰 방침(결정 2)을 다음과 같이 보완한다.
- **검색 도구용 토큰** (`GITHUB_MCP_TOKEN`): 읽기 전용 fine-grained 토큰. 필요한 저장소에만 `Metadata`, `Issues`, `Pull requests`의 읽기 권한.
- **알림 도구용 토큰** (`GITHUB_MCP_NOTIFICATIONS_TOKEN`, 선택): 클래식 토큰, 권한은 `notifications` **하나만**. 이 권한은 "읽음 표시" 같은 쓰기도 기술적으로 허용하므로 완전한 읽기 전용은 아니다. 코드가 알림에 GET만 보내고(테스트로 고정), `repo` 같은 넓은 권한이 붙은 토큰은 서버가 거부해서 피해 범위를 줄인다. 이 토큰을 만들지 않으면 알림 도구만 꺼진다(나머지는 동작).
- 이 절충은 "읽기 권한만 가진 인증" 요구에서 알림 부분에 한해 벗어난다. 사용자가 1.3에서 토큰을 만들 때 받아들일지 정한다. 받아들이지 않으면 알림 도구를 뺀다.

**서버가 토큰의 권한을 검사한다.** 클래식 토큰은 응답 헤더(`X-OAuth-Scopes`)로 권한이 보인다. `read:*`와 `notifications`만 허용하고, `repo`, `workflow`, `write:*`, `admin:*`, `delete_repo` 같은 권한이 하나라도 있으면(예: `gh auth`의 기존 토큰) 시작 시 거부한다. fine-grained 토큰은 이 헤더가 없으므로 검사할 수 없고, 사용자가 만들 때의 권한 설정과 4.1·1.3의 쓰기 거부 시험으로 확인한다.

**검색 결과 필드(공개 저장소로 확인):** 저장소(`repository_url`), 번호, 제목, 주소, 갱신 시각, 작성자, 배정자, `milestone`(`due_on` 필드 포함)이 들어 있다. 리뷰를 **요청한 사람**은 검색 결과에 없어서 PR의 타임라인(`review_requested` 이벤트의 행위자)에서 따로 얻는다. 얻지 못하면 `requestedBy`를 비우고 표시한다.

**정렬 문구 정리:** 설계의 결정 4(갱신 최신순)와 명세 시나리오의 "갱신이 이른 것부터"가 어긋나 있었다. 결정 4의 이유(가까운 마감과 최근 갱신이 중요)를 따라 **최근에 갱신된 것부터**로 하고, 명세 시나리오 문구를 이에 맞게 고쳤다.

## 실제 계정 검증 결과 (2026-10-11, 작업 4.1)

- **알림:** `gh`와 같은 50건(전부 `jwhitekim/veloo`의 CI 알림), 두 번 조회한 결과 동일, 조회 후에도 읽지 않은 알림 수 그대로(읽음 표시를 바꾸지 않음). CI 알림의 대상(`CheckSuite`)은 웹 주소로 바꿀 수 없어 `url`이 null이다.
- **배정 항목:** `gh` 검색과 같은 1건. 마일스톤 마감 원본 `2026-10-16T00:00:00Z`가 한국 날짜 `2026-10-16`으로 나오고, GitHub 웹 화면의 마감(10월 16일)과 같다. 마일스톤이 없는 항목의 `noDeadline` 표시는 단위 테스트로 확인했다.
- **리뷰 요청:** `gh`와 같은 0건. 요청 건이 없어서 **`requestedBy`(타임라인 조회)는 실제 계정으로 검증하지 못했다.** 다른 계정이 필요하며 단위 테스트로만 확인된 상태다.
- **시험 중 발견한 오류:** GitHub 검색은 쿼리에 `is:issue` 또는 `is:pr`이 반드시 있어야 한다(없으면 422). 배정 항목 조회가 이 때문에 실패했고, 이슈와 PR을 따로 검색해서 합치도록 고쳤다. 테스트의 가짜 GitHub에도 같은 규칙을 넣었다.
- **토큰 쓰기 거부(1.3):** 검색용 fine-grained 토큰으로 코멘트 작성, 이슈 생성, 이슈 수정을 시도하면 모두 403(`Resource not accessible by personal access token`).
- **시험용 데이터:** `jwhitekim/veloo-secretary`의 이슈 #1(배정, 마일스톤 `secretary`)은 시험용이다. 필요 없으면 웹에서 지워도 된다.
