# Design

## Context

GitHub에는 내게 해당하는 일을 모아 주는 조회가 이미 있다: 내게 리뷰가 요청된 PR 검색, 내게 배정된 이슈와 PR 검색, 알림 목록, 그리고 마일스톤의 마감일(`due_on`). 이 컴퓨터에는 `gh`가 `jwhitekim`으로 로그인되어 있다. 공식 GitHub MCP 서버와 여러 커뮤니티 서버가 있고, 공식 서버는 도구 묶음(툴셋)과 읽기 전용 모드를 설정으로 제한할 수 있는 것으로 알고 있다(조사 때 확인한다). 동기는 proposal.md의 Why를 본다.

## Goals / Non-Goals

**Goals:**
- 쓰기 도구가 노출될 수 없다는 것을 검증할 수 있는 읽기 전용 GitHub 도구.
- 일정 감지에 필요한 항목(리뷰 요청, 배정, 마일스톤 마감, 알림)만.

**Non-Goals:**
- 쓰기 전반, 코드 읽기, 저장소 관리.

## Decisions

### 1. 세 가지 방식을 조사하고 비교해서 고른다
(A) 공식 서버를 읽기 전용 설정으로 쓴다: 코드를 만들 필요가 없고 유지가 쉽다. 단 설정이 쓰기 도구를 실제로 숨기는지, 필요한 조회가 있는지, 의존성이 무엇인지 확인해야 한다. (B) `gh api`를 감싼 얇은 서버: 고정된 조회 명령만 실행한다. 사용자 입력이 명령에 섞이지 않게 쉘 없이 인자를 배열로 넘기고(`execFile`) 허용된 경로만 호출한다. (C) REST를 직접 호출하는 작은 서버: 의존성이 가장 적고 호출을 완전히 통제한다. 선택의 1순위 기준은 **쓰기 도구가 존재하지 않음을 테스트로 보장할 수 있는가**이다. A가 이 기준을 충족하면 A를 쓰고 이 변경은 설정과 검증 테스트가 되고, 충족하지 못하면 C를 우선한다(B는 외부 프로세스 호출이라 위험이 한 단계 더 있다).

### 2. 인증은 읽기 전용 토큰을 따로 쓴다
`gh`의 기존 로그인 토큰은 보통 쓰기 권한까지 가진다. 에이전트용으로는 필요한 저장소에 대한 읽기 권한만 가진 fine-grained 토큰을 따로 만들어 쓰는 것을 원칙으로 한다. 토큰을 만드는 일은 GitHub 설정에서 사용자가 직접 한다.

### 3. 알림 조회는 읽음 표시를 바꾸지 않는다
조회가 상태를 바꾸면 사용자가 보던 알림이 사라진다. 읽기만 하는 호출만 쓰고 읽음 표시 호출은 도구로 노출하지 않는다.

### 4. 결과는 개수 상한을 둔다
항목이 많으면 상한까지만 주고 잘림 표시를 한다. 에이전트에게는 가까운 마감과 최근 갱신이 중요하므로 정렬 기준을 갱신 최신순으로 한다.

## Risks / Trade-offs

- **공식 서버의 기본 구성에는 쓰기 도구가 포함된다.** 읽기 전용 설정을 켜도 일부가 남는지 직접 도구 목록으로 검증하기 전에는 쓰지 않는다.
- **토큰 권한이 넓으면 모델의 실수 한 번이 저장소 변경으로 이어질 수 있다.** 결정 2로 줄이고, 서버가 읽기 전용 도구만 갖도록 이중으로 막는다.
- **비공개 저장소의 제목과 본문이 로컬 모델에 들어간다.** 외부 LLM으로는 보내지 않는다는 전제를 에이전트 변경이 지킨다. 어느 저장소를 포함할지는 설정으로 제한한다.
- **이슈 본문과 PR 설명에도 지시문이 숨어 있을 수 있다(프롬프트 주입).** 방어는 에이전트 쪽에 있다.
