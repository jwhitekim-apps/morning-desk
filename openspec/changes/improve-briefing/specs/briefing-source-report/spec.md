# Spec Delta

## Purpose
브리핑이 To Do 외의 소스(메일, GitHub, 폴리오)와 집 서버 상태를 읽은 결과를 항상 보여 주도록 정한다. 후보가 없는 날에도 무엇을 읽었는지 알 수 있게 하고, 소스 내용이 카카오톡으로 나가는 범위와 [참고] 구역의 규칙, 기본 실행 시각을 함께 정해서 브리핑이 믿을 수 있고 군더더기 없게 하는 것이 목적이다.

## ADDED Requirements

### Requirement: 켜 둔 소스마다 읽은 결과를 구역으로 보고한다
시스템은 켜 둔 소스(메일, GitHub, 폴리오)마다 이번 실행에서 읽은 건수와 항목 제목을 구역으로 보고해야 한다(SHALL). 할 일 후보가 하나도 없어도 구역은 나와야 한다(SHALL). 읽은 것이 없으면 0건이라고 적어, 읽지 않은 것과 읽었으나 없던 것을 구분할 수 있어야 한다(SHALL). 항목이 상한보다 많으면 상한까지만 보여 주고 남은 개수를 알려야 한다(SHALL).

#### Scenario: 후보가 없는 날의 메일
- **WHEN** 메일 12통을 읽었으나 모델이 낸 할 일 후보가 없다
- **THEN** 메일 구역에 12통이라는 건수와 항목 제목이 나온다

#### Scenario: 읽은 것이 없음
- **WHEN** 켜 둔 GitHub에서 읽은 항목이 없다
- **THEN** GitHub 구역에 0건이라고 나오고, 구역 자체가 사라지지 않는다

#### Scenario: 항목이 상한보다 많음
- **WHEN** 새 논문이 상한보다 많다
- **THEN** 상한까지만 제목이 나오고 남은 편수가 함께 나온다

### Requirement: 꺼 둔 소스는 꺼져 있다고 알린다
시스템은 설정으로 꺼져 있거나 필요한 설정(접속 키)이 없어 읽지 않은 소스를 조용히 빼지 않고, 어느 소스가 꺼져 있는지 한 줄로 알려야 한다(SHALL). 꺼 둔 소스는 실패가 아니므로 실패 구역에 올리지 않아야 한다(SHALL NOT).

#### Scenario: 폴리오가 꺼져 있음
- **WHEN** 실행 설정에 폴리오가 켜져 있지 않다
- **THEN** 브리핑에 폴리오가 꺼져 있다는 한 줄이 나오고, 폴리오 구역과 실패 구역에는 나오지 않는다

### Requirement: 소스 내용은 제목까지만 카카오톡으로 보낸다
시스템은 메일은 제목, GitHub는 저장소 이름과 제목, 폴리오는 논문 제목까지만 카카오톡으로 보내야 한다(SHALL). 메일 보낸 사람, 메일 본문, GitHub 알림이나 이슈 본문, 논문 본문은 카카오톡으로 보내지 않아야 한다(SHALL NOT). 보내는 제목은 길이를 제한하고, 로그에는 제목을 남기지 않고 건수와 소요 시간만 남겨야 한다(SHALL).

#### Scenario: 제목 외의 내용
- **WHEN** 본문과 보낸 사람이 있는 메일을 브리핑에 넣는다
- **THEN** 카카오톡 메시지에는 제목만 들어 있고 보낸 사람과 본문은 없다

#### Scenario: 로그에 제목이 없음
- **WHEN** 소스 구역을 만든 실행의 로그를 확인한다
- **THEN** 소스별 건수와 소요 시간은 있고 제목은 없다

### Requirement: 집 서버 상태는 이상이 있을 때만 항목으로 보고한다
시스템은 하루 실행에서 설정에 적은 서비스와 컨테이너, 학교 LLM 서버를 읽기 전용으로 점검하고(SHALL), 저하·중단·점검 불가인 것만 이름과 함께 항목으로 보고해야 한다(SHALL). 모두 정상이면 한 줄로 알려야 한다(SHALL). 점검은 모델을 올리지 않아야 하고(SHALL NOT), 도커 로그의 내용은 브리핑에 넣지 않아야 한다(SHALL NOT). 점검 대상 설정이 없으면 점검을 건너뛰고 건너뛰었다는 한 줄만 알려야 한다(SHALL).

#### Scenario: 모두 정상
- **WHEN** 점검 대상이 모두 정상이다
- **THEN** 서버가 정상이라는 한 줄만 나온다

#### Scenario: 서비스가 중단됨
- **WHEN** 점검 대상 중 한 서비스가 응답하지 않는다
- **THEN** 그 서비스의 이름이 중단으로 나오고, 다른 점검 결과와 소스 구역은 그대로 나온다

#### Scenario: 점검을 못 함
- **WHEN** 도커를 쓸 수 없어 컨테이너 상태를 읽지 못한다
- **THEN** 죽은 것으로 보고하지 않고 점검 불가로 구분해서 나온다

#### Scenario: 점검 설정이 없음
- **WHEN** 점검 대상 설정 파일이 없다
- **THEN** 점검을 건너뛰었다는 한 줄만 나오고 실행은 계속된다

### Requirement: 한 소스의 실패가 다른 소스의 보고를 막지 않는다
시스템은 한 소스를 읽지 못하면 그 소스와 원인을 실패 구역에 올리고(SHALL), 나머지 소스와 서버 점검의 보고는 그대로 보여야 한다(SHALL).

#### Scenario: Gmail 로그인 만료
- **WHEN** Gmail 로그인이 만료되어 메일을 읽지 못한다
- **THEN** 실패 구역에 Gmail 로그인 만료가 나오고, GitHub와 폴리오 구역은 그대로 나온다

### Requirement: [참고] 구역에는 사용자가 알아야 할 안내만 둔다
시스템은 [참고] 구역에 태스크 추가가 꺼져 있다는 안내, 한 번에 추가할 수 있는 개수를 넘겨 추가하지 않은 건수, 모델 없이 만든 브리핑이라는 안내처럼 사용자가 알아야 할 것만 적어야 한다(SHALL). 태스크 추가가 꺼져 있을 때의 안내는 현재 상태(추가가 꺼져 있고 찾은 일은 To Do에 없다)를 그대로 말해야 한다(SHALL). 모델 출력을 코드가 걸러낸 건수는 카카오톡에 적지 않아야 하고(SHALL NOT), 로그에 사유별 건수(근거 인용 없음, 지시문 같은 제목, 중복, 소스당 상한 초과, 전체 상한 초과, 날짜 비움)로만 남겨야 한다(SHALL).

#### Scenario: 태스크 추가가 꺼져 있음
- **WHEN** 모델이 후보를 찾았으나 태스크 추가가 꺼져 있다
- **THEN** 찾은 일 N건이 To Do에 없다는 안내가 나오고, "비교"라는 표현은 쓰지 않는다

#### Scenario: 걸러낸 후보가 있음
- **WHEN** 코드가 모델의 후보 하나를 근거 인용이 없다는 이유로 걸렀다
- **THEN** 카카오톡의 [참고]에는 걸렀다는 문장이 없고, 로그에는 사유별 건수가 남는다

#### Scenario: 모델 없이 만든 브리핑
- **WHEN** 모델에 닿지 못해 모델 없이 브리핑을 만들었다
- **THEN** [참고]에 모델 없이 만든 브리핑이라는 안내가 나온다

### Requirement: 구역의 중요도 순서를 정하고 분량이 모자라면 아래부터 뺀다
시스템은 구역을 실패, 확인, 서버 이상, 먼저 할 일, 오늘, 밀린 일, 임박, 새로 찾은 일, 소스별 보고(메일, GitHub, 폴리오), 서버 정상 한 줄, 꺼진 소스, 참고 순서로 놓아야 한다(SHALL). 카카오톡 분량을 넘으면 아래쪽 구역을 구역 단위로 빼고 빠진 구역의 개수를 알려야 한다(SHALL).

#### Scenario: 서버 이상이 위쪽에 나옴
- **WHEN** 서버 점검에서 서비스 하나가 중단이고 소스 구역이 길다
- **THEN** 서버 이상은 소스별 보고보다 먼저 나온다

#### Scenario: 분량이 모자람
- **WHEN** 모든 구역을 담으면 분량을 넘는다
- **THEN** 아래쪽 구역(참고, 꺼진 소스, 소스별 보고 순)부터 통째로 빠지고 빠진 개수가 마지막에 나온다

### Requirement: 기본 실행 시각은 한국 시간 낮 12시다
시스템은 설정이 없으면 매일 한국 시간 낮 12시에 브리핑을 한 번 실행하는 것을 기본으로 해야 한다(SHALL). 브리핑의 제목과 모델에게 주는 지시문은 실행 시각에 맞지 않는 "아침"이라는 표현을 쓰지 않아야 한다(SHALL NOT).

#### Scenario: 정오 실행
- **WHEN** 한국 시간 낮 12시가 되었다
- **THEN** 브리핑이 한 번 만들어져 전송된다

#### Scenario: 제목
- **WHEN** 브리핑 첫 줄의 제목을 확인한다
- **THEN** 날짜와 요일이 있고 "아침"이라는 말은 없다
