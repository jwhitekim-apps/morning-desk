# Design

## Context

카카오 "나에게 보내기"는 메모 API(`kapi.kakao.com/v2/api/talk/memo/default/send`)에 텍스트 템플릿(본문 200자, 링크 주소 필수)을 보내는 방식이다. 액세스 토큰은 짧게 살고, `kauth.kakao.com/oauth/token`에서 리프레시 토큰으로 갱신한다. 갱신 응답에 새 리프레시 토큰이 오는 경우가 있어서 이어 쓰려면 저장해야 한다(약 60일 수명). 클라이언트 시크릿을 켠 앱은 갱신에도 그 값이 필요하다. 이전 시스템에서 이 흐름이 모두 동작했다. 읽기 API는 없다. 동기는 proposal.md의 Why를 본다.

## Goals / Non-Goals

**Goals:**
- 나에게만 보낼 수 있는, 모델이 오용할 수 없는 전송 도구.
- 토큰 갱신이 사람 개입 없이 이어진다.
- 한도 초과나 인증 만료가 조용히 사라지지 않는다.

**Non-Goals:**
- 읽기, 친구에게 보내기.
- 브리핑 나누기와 서식(비서 앱).
- 알림이 울리지 않는 문제의 해결.

## Decisions

### 1. 받는 사람을 매개변수로 두지 않는다
카카오 메모 API 자체가 본인에게만 간다. 그래도 도구 입력에 수신자 필드를 두지 않고 친구 대상 도구를 만들지 않아서, 나중에 누군가 API를 바꾸거나 모델이 인자를 지어내도 구조적으로 다른 사람에게 보낼 길이 없게 한다.

### 2. 한도를 넘으면 자르지 않고 거부한다
이전 시스템에서는 자르면 정보가 사라지고(마감, 항목), 나누면 어디서 끊을지가 읽기 품질을 좌우한다는 것을 배웠다. 어디서 어떻게 나눌지는 브리핑의 내용을 아는 쪽이 정해야 해서, 이 서버는 넘친 글자 수를 알려 거부하고 나누는 일은 비서 앱이 한다. 여러 통을 한 번에 보내는 도구는 3통까지만 받고 순서를 지킨다.

### 3. 리프레시 토큰은 로컬 파일에 원자적으로 저장한다
이전에는 서버리스라 저장소(Supabase)에 보관했다. 이번에는 파일(홈 폴더 아래, 파일 600)이다. 쓰다가 중단되어 파일이 깨지지 않도록 임시 파일에 쓴 뒤 이름을 바꾸는 방식으로 교체한다. 환경 변수의 값은 최초 시작 값이고, 파일이 있으면 파일이 우선한다.

### 4. 인증 오류에는 한 번만 갱신하고 재시도한다
전송이 인증 오류로 거부되면 한 번 갱신하고 다시 보낸다. 갱신도 실패하면(리프레시 토큰 만료) 반복하지 않고 다시 로그인하라는 오류를 알린다. 서버 일시 장애(5xx)는 구분해서 알리고 보냈는지 불확실한 상태가 되지 않도록 "보내지 못했다"를 분명히 한다.

### 5. 드라이런이 있다
브리핑 시험 때 실제로 보내지 않고 내용만 확인하려고 둔다. 한도 검사는 실제 전송과 같게 적용한다.

### 6. 링크 주소는 설정 값이다
템플릿이 링크를 요구해서 설정 값(`KAKAO_LINK_URL`)을 받는다. 이전에는 서버 주소였지만 이번에는 보고를 누르면 열 곳(예: To Do 웹 주소)을 사용자가 정한다.

## Risks / Trade-offs

- **알림이 울리지 않는다.** 보낸 메시지는 도착하지만 폰 알림이 오지 않는 것이 실제로 확인되었다. 이 서버로는 해결되지 않고, 브리핑이 읽히지 않을 위험이 남는다. 대안 알림 경로는 별도 변경이다.
- **리프레시 토큰이 약 60일이면 만료될 수 있다.** 이전 운영에서는 갱신 때마다 연장되는 것으로 보였지만 확인된 사실은 아니다. 매일 쓰므로 거의 매일 갱신되어 문제가 없을 것으로 보되, 만료 시에는 오류로 분명히 알린다.
- **동시 실행**: 두 프로세스가 동시에 갱신하면 한쪽 토큰이 무효가 될 수 있다. 하루 한 번 실행이라 실제 위험은 작고, 파일 교체를 원자적으로 하는 것으로 줄인다.
