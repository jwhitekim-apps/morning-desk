# Design

## Context

`mcp/microsoft-todo/`는 `fabienbutz/microsoft-todo-mcp`(MIT) @83d8f44의 일부를 골라 가져온 것이다. 구조는 `auth/`(기기 코드 로그인, 토큰 캐시), `graph/`(Graph 클라이언트, 오류 분류, 페이지 넘김), `todo/`(목록·태스크 서비스), `tools/`(도구 정의, 위험 등급), `server.ts`(조립)로 나뉜다. 도구는 `defineTool`로 정의하고 위험 등급(`read`, `write`)으로 서버가 노출을 거른다. 로컬에서 표준입출력으로 도는 서버이며 HTTP 서버를 열지 않는다. 동기는 proposal.md의 Why를 본다.

원본의 중복 방지(`IdempotencyCache`)는 같은 프로세스 안에서 시간 제한 안의 재시도에만 통하고 재시작하면 사라진다(코드 주석에 명시). 오류는 `auth_required`, `auth_expired`, `permission_denied`, `rate_limited`, `graph_unavailable` 등으로 분류되어 이미 구분된다.

## Goals / Non-Goals

**Goals:**
- 에이전트가 의존할 동작을 스펙으로 확정하고, 도구 표면을 테스트로 고정한 상태를 유지한다.
- 브리핑에 필요한 "기간별 마감 조회"를 도구 호출 한 번으로 만든다.
- 한국 표준시에서 날짜가 하루 어긋나지 않게 한다.
- 에이전트가 매일 새로 실행되어도 같은 태스크가 중복으로 쌓이지 않게 한다.

**Non-Goals:**
- 수정, 완료, 삭제, 목록 관리, 체크리스트 도구. 위임 정책상 에이전트에게 주지 않는다.
- 반복 일정과 변경분 조회(delta). 필요가 확인되면 다음 변경에서 다룬다.
- 본인 Azure 앱 등록으로의 전환, 원격 호스팅(HTTP), 에이전트와 다른 데이터 소스.

## Decisions

### 1. 도구 표면은 허용 목록 테스트가 지킨다
`test/registry.test.ts`가 도구 이름 목록을 허용 목록과 정확히 비교하고 위험 등급이 `destructive`인 도구가 없음을 검사한다. 이번 변경은 허용 목록에 `list_tasks_due` 한 줄을 의도적으로 추가한다. 도구를 코드에 두지 않는 것이 "숨기기 스위치"보다 강한 방어다(스위치가 꺼져 있으면 도구가 노출될 수 있다).

### 2. 마감 범위 조회는 목록별 조회를 모아서 클라이언트에서 거른다
Graph의 To Do 태스크 조회는 서버에서 날짜 조건을 거는 것을 믿을 수 없다. 그래서 `GET /me/todo/lists`로 목록을 얻고, 목록마다 미완료 태스크(`status ne 'completed'`)를 가져와 마감 날짜(한국 표준시)로 거른다. 구현할 때 서버 쪽 `$filter`를 쓸 수 있는지 확인하고, 되면 쓴다. 목록 수와 태스크 수는 개인 사용 규모(수십 개)라서 모아서 거르는 비용이 작다. 호출은 목록 수만큼이므로 동시에 여러 개를 보내되 개수를 제한하고, 한 목록의 실패가 전체를 망치지 않도록 실패한 목록 이름을 결과에 함께 알린다(조용히 빠뜨리지 않는다). 결과는 마감, 제목 순으로 정렬하고 한도(기본 200)를 넘으면 잘렸다는 표시와 남은 개수를 붙인다.

### 3. 시간 변환은 한 모듈에 모은다
한국 표준시(`Asia/Seoul`) 변환을 한 파일의 순수 함수로 모은다: 날짜 문자열을 한국 날짜로, Graph가 돌려주는 `{dateTime, timeZone}`을 한국 날짜와 시각으로, 입력 일시를 Graph 형식으로. 시간대 규칙이 흩어지면 하루 어긋나는 오류가 숨기 때문이다. 환경 변수로 시간대를 바꿀 수 있게는 하지 않는다(개인 한국 사용이므로 상수로 둔다). 하루 경계(한국 자정 전후)는 속성 기반 테스트(원본 devDependency `fast-check`)로 검증한다.

**실측(2026-10-10, 개인 계정, 읽기 전용 로그인)**: 앱에서 날짜만 고른 마감은 Graph에서 `{"dateTime": "2026-04-08T15:00:00.0000000", "timeZone": "UTC"}`처럼 온다. 즉 한국 시간 자정(다음 날 00:00)이 UTC로 표현된 것이어서, 날짜 부분만 잘라 쓰면 하루 전으로 보인다(위 값의 실제 마감은 4/9). 표본 3건이 모두 15:00 UTC였다. 변환은 `timeZone`이 UTC이면 한국 시간으로 옮긴 뒤 날짜를 취하는 방식이어야 하고, 이 값을 테스트 고정값으로 쓴다. 알림 시각이 있는 태스크의 모양은 아직 관찰하지 못했다.

### 4. 중복 방지는 "만들기 전에 확인"으로 보강한다
원본의 프로세스 내 캐시는 유지하고(같은 실행의 연타를 막는 값싼 방어), 그 위에 `create_task` 안에서 **같은 목록의 미완료 태스크 중 이름과 마감 날짜가 같은 것이 있는지 먼저 조회**한다. 있으면 새로 만들지 않고 기존 태스크를 `alreadyExisted: true`로 돌려준다. 재시작해도 저장소가 곧 To Do 자체라서 항상 유효하다. 비용은 추가마다 목록 조회 한 번이다. 이름 비교는 앞뒤 공백을 제거하고 대소문자는 구분하지 않으며, 그 외의 유사도 판단은 하지 않는다(모델이 만든 비슷한 이름은 에이전트가 다룬다). 이전 시스템에서 단축어 재시도로 같은 태스크가 중복 생성된 경험에서 나온 결정이다.

### 5. 검증은 모의 테스트와 실제 계정 시험을 나눈다
모든 동작은 Graph를 모의하는 단위 테스트로 검증하고(네트워크 없음), 실제 계정에서는 한 번씩만 확인한다: 읽기 전용 로그인으로 목록과 마감 조회, 쓰기 권한으로 재로그인해 시험 태스크 1건 추가. 시험 태스크는 삭제 도구가 없으므로 사용자가 앱에서 지운다. 읽기 전용 권한부터 시작해 쓰기 권한은 읽기가 확인된 뒤에 요청한다.

## Risks / Trade-offs

- **목록마다 호출하는 조회는 목록이 많아지면 느리다.** 개인 규모에서는 괜찮고, 동시성 제한과 한도로 막는다. 느려지면 서버 쪽 필터나 delta를 다음 변경에서 검토한다.
- **중복 판정이 이름과 마감 일치에만 의존한다.** 이름이 조금 다르면 중복이 생길 수 있다. 에이전트가 만들기 전에 마감 범위 조회로 비슷한 것을 확인하는 규칙은 에이전트 쪽에서 다룬다.
- **Graph의 마감 일시는 날짜 중심으로 저장되어 시각 처리가 미묘하다.** 시간대가 붙은 값이 앱에서 하루 다르게 보이는 문제가 가장 위험해서, 한국 자정 경계를 가장 먼저 테스트한다. 실제 계정에서 앱 표시와 비교하는 시험을 둔다.
- **기본 클라이언트는 Microsoft의 공개 명령줄 도구용 클라이언트다.** 제3자 도구가 쓰는 것이 약관상 애매할 수 있고 동의 화면 이름이 다르다. 이번 변경에서는 시험용으로만 쓰고 본인 앱 등록은 다음 변경으로 미룬다.
- **의존성 취약점 경고 10개.** 표준입출력 서버라 노출은 작다고 보지만 확신하지 않는다. 이번 변경에서는 `npm audit fix`가 안전하게 되는지만 조사해서 결과를 기록한다.

## 실측 보충 (2026-10-10, 쓰기 권한 시험)

마감(`dueDateTime`)은 날짜만 저장된다. Graph는 보낸 시각을 버리고 **보낸 시간대 기준의 날짜**를 그 시간대 자정으로 저장한다. 시험 태스크로 확인한 결과:

| 보낸 값 | 저장되어 돌아온 값 |
|---|---|
| `2026-10-11T00:00` `Asia/Seoul` | `2026-10-10T15:00` UTC (앱이 저장하는 모양과 같다) |
| `2026-10-10T15:00` UTC (한국 10/11 자정을 UTC로 바꾼 값) | `2026-10-10T00:00` UTC (하루 어긋남) |
| `2026-10-11T00:00` UTC | `2026-10-11T00:00` UTC |

그래서 마감은 한국 날짜를 `Asia/Seoul` 자정으로 보낸다. 알림(`reminderDateTime`)은 시각이 그대로 저장되므로 UTC 변환이 맞다. 처음에 마감도 UTC로 보내 중복 방지가 어긋났고(같은 요청이 새 태스크로 생겼다), 이 규칙으로 고친 뒤 같은 요청이 `alreadyExisted: true`로 처리되는 것을 확인했다.
