# Tasks

## 1. 서버 기반

- [ ] 1.1 `mcp/server/`에 서버 골격(설정, 오류 분류, 로거, 도구 등록)을 만든다. 다른 MCP 서버와 같은 구조(위험 등급 타입에 쓰기 등급 없음, 허용 필드만 남기는 로거)를 따른다. 검증: 빈 도구 목록으로 서버가 시작되고 타입 검사, 린트, 테스트, 빌드가 통과한다
- [ ] 1.2 점검 대상 설정을 읽고 검증한다(서비스 이름과 주소 또는 호스트:포트, 컨테이너 이름, 모델 서버 주소와 기대 모델). 잘못된 항목(컨테이너 이름 모양, 주소 형식)은 거부하고, 평문 주소를 쓰면 경고 표시를 붙인다. 검증: 테스트에서 올바른 설정은 읽히고, 이름에 공백·`;`·`$`가 든 컨테이너와 주소가 아닌 값은 설정 오류가 되며, 점검 대상이 하나도 없으면 설정 누락 오류가 난다

## 2. 서비스 점검

- [ ] 2.1 HTTP 응답과 TCP 포트 연결을 점검한다(대상별 제한 시간, 응답 시간, 상태 네 가지 구분, 한 대상의 실패가 나머지를 멈추지 않음, 동시 수 제한). 검증: 모의 서버 테스트에서 정상, 느린 응답(저하), 응답 없음(중단), 연결 거부가 각각 기대한 상태로 나오고, 한 서비스가 죽어도 나머지 결과가 나온다
- [ ] 2.2 도커 컨테이너 상태를 점검한다(`docker inspect`의 실행 상태, 재시작 횟수, 건강 검사). 도커가 없거나 권한이 없으면 점검 불가로 구분한다. 검증: 가짜 실행기 테스트에서 실행 중은 정상, 재시작이 잦거나 건강 검사 실패는 저하, 중지는 중단이고, 도커 오류는 컨테이너가 죽었다는 결과가 아니라 점검 불가가 된다

## 3. LLM 점검

- [ ] 3.1 학교 모델 서버를 단계별로 점검한다(포트 연결, `GET /v1/models`의 응답과 인증, 기대 모델 존재). 앞 단계가 막히면 뒤 단계는 점검하지 않았다고 표시하고, 모델에게 글을 생성하게 하는 호출은 코드에 두지 않는다. 검증: 모의 서버 테스트에서 포트 닫힘, 키 거부, 기대 모델 없음, 정상이 각각 구분되어 나오고, 정상일 때도 `/v1/models` 외의 요청이 한 번도 나가지 않는다

## 4. 도커 로그 요약

- [ ] 4.1 컨테이너 로그를 고정 인자로 조회한다(`docker logs --since --tail`, 쉘 없이, 시간 최대 72시간과 줄 수 최대 5000의 상한, 잘림 표시). 설정에 없는 이름은 도커에 요청하지 않고 거부한다. 검증: 가짜 실행기 테스트에서 실제로 실행된 인자가 기대와 정확히 같고, 설정에 없는 이름과 상한을 넘는 값은 실행 없이 입력 오류가 되며, 상한에 걸리면 잘림 표시가 있다
- [ ] 4.2 오류로 보이는 줄을 찾아 정규화하고 묶어서 개수와 짧은 요약(기본 5개, 각 200자 이내)을 만든다. 토큰·비밀번호로 보이는 값과 긴 식별자는 가리고 응답에 데이터 표시를 붙인다. 검증: 테스트에서 같은 오류 100줄이 하나로 묶여 개수 100으로 나오고, 오류가 없으면 0건이며, `Bearer ...`·`password=...`·`api_key=...`·긴 16진수가 요약에 그대로 나오지 않고, 응답에 원문이 없다

## 5. 도구와 보호 테스트

- [ ] 5.1 도구 4개(`list_targets`, `check_services`, `check_llm`, `summarize_docker_logs`)를 연결하고 허용 목록 테스트와 입력 정의 테스트를 만든다. 검증: 도구 이름이 허용 목록과 정확히 같고, 쓰기·실행에 해당하는 이름이 없으며, 입력 정의에 주소·포트·명령·경로 필드가 없고 컨테이너는 설정 목록 안의 이름만 받는다
- [ ] 5.2 코드 구조 테스트를 만든다: 외부 프로세스는 `docker`만 실행하고 쉘을 쓰지 않으며, 학교 서버로 나가는 요청은 `/v1/models`뿐이고 `/chat/completions` 등 생성 경로가 소스에 없다. 검증: 소스 검사 테스트가 통과하고, 금지된 경로나 쉘 사용을 일부러 넣으면 실패한다
- [ ] 5.3 서버 자신의 로그와 응답에 키와 로그 원문이 없는지 확인하는 테스트를 만든다. 검증: 모든 도구를 정상·실패 경로로 실행한 뒤 수집한 로그와 응답에서 키와 로그 원문이 발견되지 않고, 일부러 로그에 넣으면 테스트가 실패한다

## 6. 실제 검증 (사용자와 함께)

- [ ] 6.1 이 컴퓨터에서 실제 학교 모델 서버를 점검한다(정상, 일부러 틀린 키, 일부러 틀린 포트). 검증: 정상이면 모든 단계가 정상이고, 틀린 키는 인증 단계 실패, 틀린 포트는 포트 단계 중단으로 나오며, 점검 때문에 모델이 메모리에 올라오지 않는다(모델 호출이 없음을 요청 기록으로 확인)
- [ ] 6.2 집 서버에서 서비스, 컨테이너 상태, 도커 로그를 점검한다(이 컴퓨터는 도커가 꺼져 있고 집 서버가 아니라서 사용자와 함께 집 서버에서 한다). 검증: 사용자가 아는 서비스 상태와 일치하고, 최근 로그의 오류 개수가 `docker logs`를 직접 센 값과 맞으며, 요약에 비밀이 없다
- [ ] 6.3 도커 권한 방침을 정한다: 서버를 도커 그룹 권한으로 돌릴지, 읽기 전용 도커 소켓 프록시를 앞에 둘지. 검증: 결정과 이유가 `design.md`에 기록되어 있고, 프록시를 쓰기로 하면 쓰기 요청이 프록시에서 거부되는 것을 확인한다
