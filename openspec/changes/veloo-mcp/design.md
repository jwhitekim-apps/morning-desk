# Design

## Context

벨루는 별개의 FastAPI + React 프로젝트(`veloo.2joon.com`, 집 서버의 Docker)이고 쿠키 세션 로그인(`POST /login` → `access_token` 쿠키)을 쓴다. 태스크는 `/todo/api/todos`, 주간 리뷰는 `/todo/api/reviews/weekly`에서 읽는다. 이 API는 공개 계약이 아니라 벨루 자신의 프런트엔드가 쓰는 내부 API다. 이전 시스템의 어댑터가 이 경로로 로그인, 목록, 주간 리뷰, 생성을 모두 실제로 수행했다. 이번에는 읽기만 남긴다. 동기는 proposal.md의 Why를 본다.

## Goals / Non-Goals

**Goals:**
- 벨루 코드를 건드리지 않고 태스크와 주간 리뷰를 안전하게 읽는다.
- 벨루가 바뀌어 응답 모양이 달라지면 조용히 틀리지 않고 알아챈다.

**Non-Goals:**
- 벨루에 쓰기(생성, 수정, 삭제). 새 태스크는 To Do가 받는다.
- 벨루 코드, 스키마, 서버 설정 변경.
- 기존 태스크의 To Do 자동 이관.

## Decisions

### 1. 이전 어댑터를 바탕으로 읽기만 남겨 다시 쓴다
내 코드라서 출처 표시 문제는 없다. 로그인, 세션 재사용, 401 시 한 번 재로그인은 그대로 가져오고, 생성과 우선순위 변환(`urgent`/`mid`/`normal`)은 쓰기 쪽 개념이라 제외한다.

### 2. 세션은 로컬 파일(권한 600)에 저장한다
이전에는 서버리스 환경이라 Supabase 저장소에 세션을 저장했다. 이번에는 집 서버의 프로세스라서 홈 폴더 아래 파일이면 충분하다. 세션 값과 계정 정보는 로그와 응답에 나오지 않는다.

### 3. 응답 모양을 검사한다
벨루 응답은 비공식이라 필드 이름이나 형식이 바뀌어도 알려 주지 않는다. 필수 필드(번호, 이름, 마감, 완료 여부 등)를 검사하는 스키마를 두고 어긋나면 "계약 변경" 오류로 알린다. 이전에는 우선순위 값이 어긋나(`high`/`low` 대 `urgent`/`mid`/`normal`) 한참 뒤에야 발견했다.

### 4. 마감 필터는 서버가 아니라 이쪽에서 한다
벨루의 목록 API는 필터를 받지 않고 전체를 돌려준다. 개인 규모에서는 전체를 받아 이쪽에서 완료 여부와 마감 범위로 거른다. 마감이 날짜 형식이 아닌 자유 문구인 태스크는 날짜로 해석하지 않고 원문을 그대로 돌려준다(이전에 "이번 주 안에" 같은 값을 만난 적이 있다).

### 5. 도구는 읽기 두 개뿐이다
목록 조회와 주간 리뷰. 쓰기 도구가 없는 것을 허용 목록 테스트가 지킨다.

## Risks / Trade-offs

- **벨루 내부 API가 바뀌면 깨진다.** 응답 검사(결정 3)로 빨리 알아채지만 고치는 일은 따로 해야 한다.
- **벨루 계정의 비밀번호가 약하다**는 점이 알려져 있고, 바꾸지 않기로 한 상태다. 이 서버는 그 계정 정보를 환경 변수로 받으므로 유출 시 영향이 있다. 환경 변수 파일의 권한과 저장소 제외를 지킨다.
- **벨루 서버가 집 서버에 있어 꺼져 있으면 읽지 못한다.** 연결 오류로 구분해 알리고, 에이전트는 벨루 없이도 브리핑이 나가야 한다.
- 벨루를 퇴역하면 이 서버도 필요 없어진다. 지금은 참고 자료 때문에 유지한다.
