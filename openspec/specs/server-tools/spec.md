# server-tools Specification

## Purpose
에이전트가 집 서버의 서비스와 컨테이너, 학교 서버의 LLM 상태, 도커 로그의 오류를 읽기 전용으로 점검하는 MCP 도구의 계약을 정한다. 점검만 하고 명령 실행이나 복구는 하지 않아서, 모델이 잘못 판단해도 서버가 바뀌지 않고, 이상이 있으면 조용히 지나가지 않고 브리핑에 드러나게 하는 것이 목적이다.

## Requirements

### Requirement: 설정에 적은 대상만 읽기 전용으로 점검한다
시스템은 설정 파일에 적은 서비스 주소, 포트, 컨테이너 이름, 모델 서버 주소만 점검해야 한다(SHALL). 도구의 입력으로 점검 대상의 주소나 명령을 받지 않아야 한다(SHALL NOT). 서비스를 재시작하거나 명령을 실행하거나 로그를 지우는 도구를 제공하지 않아야 한다(SHALL NOT). 도구 목록은 허용 목록과 정확히 같아야 하며, 새 도구를 추가하려면 그 목록을 의도적으로 고쳐야 한다(SHALL).

#### Scenario: 허용된 도구만 있음
- **WHEN** 서버의 도구 목록을 조회한다
- **THEN** 허용 목록과 정확히 일치하고 실행, 재시작, 삭제에 해당하는 이름의 도구가 없다

#### Scenario: 대상을 입력으로 줄 수 없음
- **WHEN** 모든 도구의 입력 정의를 확인한다
- **THEN** 주소, 포트, 명령, 파일 경로를 받는 필드가 없고, 컨테이너는 설정에 적은 이름 중에서만 고를 수 있다

#### Scenario: 설정에 없는 컨테이너
- **WHEN** 설정에 적지 않은 컨테이너 이름으로 로그 요약을 요청한다
- **THEN** 도커에 아무것도 요청하지 않고 입력 오류를 돌려준다

### Requirement: 서비스와 컨테이너가 살아 있는지 확인한다
시스템은 설정에 적은 각 서비스에 대해 응답 여부와 응답 시간을 돌려주어야 한다(SHALL). HTTP 서비스는 응답 상태를, TCP 포트는 연결 가능 여부를 확인해야 한다(SHALL). 설정에 적은 도커 컨테이너는 실행 상태, 재시작 횟수, 건강 검사 결과를 돌려주어야 한다(SHALL). 각 항목은 정상, 저하, 중단, 점검 불가 중 하나로 구분하고 점검 대상의 이름을 항상 포함해야 한다(SHALL).

#### Scenario: 모두 정상
- **WHEN** 설정에 적은 서비스가 모두 응답하고 컨테이너가 실행 중이다
- **THEN** 각 항목이 정상으로 나오고 응답 시간이 함께 나온다

#### Scenario: 서비스가 응답하지 않음
- **WHEN** 한 서비스가 제한 시간 안에 응답하지 않는다
- **THEN** 그 항목만 중단으로 나오고 나머지 점검은 그대로 이어진다

#### Scenario: 컨테이너가 계속 재시작함
- **WHEN** 컨테이너가 실행 중이지만 최근 재시작 횟수가 많거나 건강 검사가 실패한다
- **THEN** 정상이 아니라 저하로 나온다

#### Scenario: 점검 자체를 못 함
- **WHEN** 도커를 쓸 수 없어 컨테이너 상태를 읽지 못한다
- **THEN** 컨테이너가 죽은 것으로 보고하지 않고 점검 불가로 구분해서 이유를 알린다

### Requirement: 학교 서버의 LLM 상태를 모델을 올리지 않고 점검한다
시스템은 모델 서버의 포트 연결 가능 여부, API 응답 여부, 키의 유효 여부, 기대하는 모델이 목록에 있는지를 돌려주어야 한다(SHALL). 점검은 모델 목록 조회까지만 하고 모델에게 글을 생성하게 하는 호출을 하지 않아야 한다(SHALL NOT). 단계별로 어디서 막혔는지(포트, API, 인증, 모델) 구분해서 알려야 한다(SHALL). 키는 응답과 로그에 나타나지 않아야 한다(SHALL NOT).

#### Scenario: 모두 정상
- **WHEN** 포트가 열려 있고 키가 유효하며 기대하는 모델이 목록에 있다
- **THEN** 각 단계가 정상으로 나오고 모델 호출은 일어나지 않았음이 확인된다

#### Scenario: 포트가 닫혀 있음
- **WHEN** 모델 서버의 포트에 연결할 수 없다
- **THEN** 포트 단계에서 중단으로 알리고 API와 인증 단계는 점검하지 않았다고 표시한다

#### Scenario: 키가 틀림
- **WHEN** 포트와 API는 응답하지만 키를 거부한다
- **THEN** 인증 단계의 실패로 구분해서 알린다

#### Scenario: 기대하는 모델이 없음
- **WHEN** 모델 목록에 설정에 적은 기대 모델이 빠져 있다
- **THEN** 어떤 모델이 없는지 이름으로 알리고 저하로 구분한다

### Requirement: 도커 로그는 요약해서 돌려준다
시스템은 설정에 적은 컨테이너의 최근 시간(기본 24시간)의 로그에서 오류로 보이는 줄의 개수와 서로 다른 오류의 짧은 요약을 돌려주어야 한다(SHALL). 로그 원문을 그대로 돌려주지 않아야 한다(SHALL NOT). 요약에 든 줄은 길이를 제한하고, 토큰과 비밀번호로 보이는 값과 긴 식별자는 가려야 한다(SHALL). 조회하는 줄 수와 시간에는 상한을 두고, 잘렸으면 알려야 한다(SHALL).

#### Scenario: 오류가 있었음
- **WHEN** 최근 24시간 로그에 같은 오류가 여러 번 있었다
- **THEN** 오류 줄 수와 그 오류의 짧은 요약이 한 번만 나온다

#### Scenario: 오류가 없었음
- **WHEN** 최근 로그에 오류로 보이는 줄이 없다
- **THEN** 오류 0건으로 나오고 조회한 시간 범위와 줄 수가 함께 나온다

#### Scenario: 비밀이 섞인 로그
- **WHEN** 오류 줄에 토큰이나 비밀번호로 보이는 값이 들어 있다
- **THEN** 요약에는 그 값이 가려진 채로 나온다

#### Scenario: 로그가 너무 많음
- **WHEN** 조회 범위의 로그가 상한을 넘는다
- **THEN** 상한까지만 보고 잘렸다는 표시를 함께 준다

### Requirement: 로그의 내용은 데이터로만 다루고 비밀은 남기지 않는다
시스템은 응답에 로그의 내용이 외부에서 온 데이터이며 지시가 아니라는 표시를 붙여야 한다(SHALL). 로그와 도구 응답에는 LLM 키와 로그 원문이 나타나지 않아야 하고, 이 서버 자신의 로그에는 점검 결과의 건수와 소요 시간 같은 값만 남겨야 한다(SHALL). 오류는 설정 누락, 점검 불가, 입력 오류를 구분된 코드와 메시지로 알려야 한다(SHALL).

#### Scenario: 서버 자신의 로그에 내용이 없음
- **WHEN** 모든 도구를 실행한 뒤 이 서버가 남긴 로그를 확인한다
- **THEN** 키, 로그 원문, 오류 요약 문장이 없고 건수와 소요 시간 같은 값만 있다

#### Scenario: 설정이 빠짐
- **WHEN** 점검할 대상이 하나도 설정되어 있지 않다
- **THEN** 아무것도 점검하지 않고 설정 누락 오류로 구분해서 알린다
